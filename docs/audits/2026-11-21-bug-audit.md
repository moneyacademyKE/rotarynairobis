## BLOCKERS

### B1. Classification is fully broken — site photo content frozen since Nov 14 (ACTIVE OUTAGE)
- Evidence (local `classification_jobs`): **60 failed / 19 done / 0 pending**. Done window ends `2026-11-14 21:50`; failed window runs `2026-11-14 21:30 → 2026-11-20 17:00`.
- Chain: main model `ag/gemini-3.8-flash-high` returns **403 "model disabled in your preferences"** (inferhub dashboard setting) → fallback `gemini-3.1-flash-lite-preview` returns **400 API_KEY_INVALID**.
- Root cause of fallback death: `GEMINI_API_KEY` in `~/.opencrabs/projects/rotary-local/.env.sh` is a **16-character placeholder** (Google keys are 39 chars, `AIza…`). The same bogus value sits in `~/Documents/rotarynairobis/.dev.vars:4` — it was copied faithfully at cutover, never validated. No valid Gemini key exists anywhere on this machine.
- Impact: every new photo since Nov 14 is untyped → absent from all type-filtered galleries. DB has posts through `2026-11-20 17:00:45`; galleries' newest row is `2026-11-14 21:50:07`. Ingestion itself is healthy (offset advancing, 4,273 posts).
- Failed jobs are terminal (`local/classify.ts:110`, `attempts < 3` at `:82`) with **no requeue path** — fixing the provider alone will not heal the 60 stuck photos.
- Cron reports repeatedly claimed "Gemini fallback used" while jobs were actually failing — the receipts narrated the code path, not the outcome.
- Fix (owner decision, one of): (a) re-enable `ag/gemini-3.8-flash-high` in inferhub Dashboard → Models & pricing (the chosen main model; one toggle); (b) supply a valid Gemini key; (c) pick another enabled inferhub model (tested `gemini-3.1-flash-lite` / `gemini-3.5-flash-lite`: catalog-listed but **404 not routable** on this account). Then: requeue the 60 failed jobs + add a requeue utility.

### B2. Dormant worker's unauthenticated self-heal can flip ingestion back to Cloudflare (data-loss window)
- `src/routes/api/telegram/index.ts:19-27`: `onGet` re-registers the webhook to **the request's origin** with no auth. The worker is still live at `rotarynairobis.iamkingori.workers.dev` (verified: root 302; `workers_dev` not disabled in `wrangler.toml`).
- Any stray GET to that URL re-arms the webhook → Telegram delivers to the CF worker (writes D1, not local) → local poller 409s → its self-heal deletes the webhook → next GET re-arms. Flapping.
- Updates delivered to a webhook are confirmed by Telegram and **never returned by getUpdates** — with the mirror cron stood down post-cutover, posts landing in a flap window are lost to the local site permanently.
- The local server deliberately omits the token (`local/server.ts:10-12`) so local GETs are inert — the exposure is the workers.dev origin only.
- Fix: gate the heal behind `TELEGRAM_SECRET_TOKEN` (diagnostics can stay public) and deploy; or set `workers_dev = false` (removes the dormant fallback too — runbook trade-off).

## WARNINGS

### W1. Tick's rebuild never reaches the served cache (latent 48h staleness)
`local/tick.ts:65` → `local/build.ts:40` writes `generated/*.json`; the server serves FileKV `kv/` entries (`src/lib/gallery.ts:143`, TTL 48h at `:28`). Nothing bridges the two stores. Currently masked: KV refills on TTL expiry read-through from the same DB (probe: kv newest == gen newest on all five keys). Once B1 is fixed, new content will still take **up to 48h** to appear despite "galleries rebuilt" every 5 minutes. Fix: tick should call `publishAll` against the same FileKV (one publisher), retiring the duplicate `build.ts` path.

### W2. Poison update wedges the poll offset forever
`local/poller.ts`: a permanent `getFile` failure (expired/invalid file_id → 400, retries don't help) throws out of `ingestUpdate`; the offset advance at `:161` is all-or-nothing after the loop → the same update is retried every 5 minutes indefinitely, blocking all later updates. Fix: per-update failure isolation — record the raw fact, mark the update failed, advance past it.

### W3. Swallowed photo download → permanently unclassified photo
`local/poller.ts:95`: `downloadPhoto(...).catch(() => {})` — on failure the fact still references the file and a job is enqueued, but `drainJobs` skips jobs whose bytes are missing **without burning attempts** → pending forever. (Probe: 0 currently pending — latent.) Fix: re-download in drain from the stored file_id, or fail the job explicitly.

### W4. Sync timestamp-mode truncation never advances
`src/routes/api/sync/index.ts:49`: `since` branch orders by `tx_id` and parks the cursor at the last sent **tx_id**, but a timestamp-mode client has no timestamp cursor in `meta` — with >500 matching rows it re-requests the same `since` and gets the same page forever. tx_id mode is correct. Fix: return a `created_at` cursor (and order by it) for since-mode.

### W5. Events "Upcoming" heuristic + date parser bugs
- `src/routes/twitter/index.tsx:62`: `index < 6 && hasFutureKeyword` force-promotes the 6 newest posts containing "register"/"join us"/etc. to Upcoming **regardless of date** (a recap mentioning "registration" qualifies). This is the known "old events at top" symptom.
- `src/lib/twitter-parser.ts:25`: numeric dates parsed **DD.MM.YYYY only** — US-style MM/DD/YYYY swaps month/day; `new Date(year, 12, …)` silently rolls into next year (no month/day validation).
- `:17`: `new Date("YYYY-MM-DD HH:MM:SS")` is **Invalid Date in Safari**; the weekday/relative branches return it unchecked → "Invalid Date" rendered / everything falls to Previous on WebKit.
- Year inference uses the post's creation year — "Jan 15" posted in December resolves to the past January.
- Hardcoded fallback base `new Date(2026, 4, 19)`; month regex lacks a leading word boundary ("marching 5" → March 5).
- Fix: parse to ISO safely, validate ranges, infer year across rollover, and drop the keyword heuristic (a post is Upcoming only if its parsed date is future).

### W6. Local admin endpoints inert — docs drift
`local/server.ts` omits `TELEGRAM_SECRET_TOKEN` from route env, so `/api/publish` (the documented "publish now" escape hatch) and `/api/reprocess` fail closed locally. The self-heal only needs `TELEGRAM_BOT_TOKEN` omitted; the SECRET can safely be present. Fix: add SECRET to route env, keep BOT_TOKEN out; or document inertness.

### W7. Local schema drift
`schema.sql:87-88` has composite `(created_at, tx_id)` indexes (the D1 sync-trap fix); `local/sqlite-store.ts` SCHEMA lacks them (also `idx_media_facts_type`, `idx_posts_facts_account`). Local since-mode sync pays the scan+sort the D1 fix eliminated. Fix: derive local schema from `schema.sql` (one source of truth).

### W8. Inbound auth falls back to a third-party API key
`src/routes/api/classify/index.ts:50`: absent `CLASSIFY_API_SECRET`, the endpoint authenticates callers with `GEMINI_API_KEY` — a key that travels to Google and sits in repo history. Set a dedicated secret.

## NITS

- Two D1 adapters: `local/sqlite-store.ts:59` `Stmt.first()` silently drops bound args and has no `.bind()`; `local/platform.ts` `D1Stmt` is the complete one. Only unbound queries use the weak one today — a landmine. Consolidate.
- `local/d1-remote.ts`: `rows()` and `delta()` are identical implementations.
- Non-atomic writes: `local/kv.ts` `writeFileSync` (torn JSON → cache miss, self-heals) and `local/build.ts`. tmp+rename is cheap insurance given this repo's concurrent-writer history.
- KV dir unbounded: 1,264 files, expired entries never GC'd (`local/kv.ts`). Media cache: 669 files.
- `src/entry.local.tsx:101,153`: 500 bodies return `String(e)` — internal error detail leaks to public responses.
- `package.json:23`: `"lint": "echo 'Skipping linting…'"` — fake lint (issue #1, open since July). Package name still `my-qwik-empty-starter`.
- `src/routes/api/reprocess/index.ts`: `LIMIT ${limit}` interpolation (sanitized numeric — safe, but smells); uses `posts`/`media` views that don't exist locally (inert there behind fail-closed auth).
- Events loader dedupes by normalized text — two distinct posts with identical copy collapse into one.
- `parseEventDate` "no fellowship this Tuesday" returns a date for a cancellation → rendered as an upcoming event.

## GOOD CALLS (preserve)

- Epochal fact ledger + latest-fact-wins semantics, retractions honored (`src/lib/gallery.ts`).
- WAL mode on every open (`local/sqlite-store.ts`) — server reads concurrent with tick writes are safe.
- DI-shaped poller/classifier tests: 27 local tests run with zero network/token.
- Photo bridge: traversal-guarded, disk-first, stale-file_id self-eviction (`src/lib/photo-source.ts`), token-bearing URLs never logged (`local/telegram-read.ts`).
- Watermark-skip publish (quiet nights cost 2 indexed reads); cursor advances only on clean publish.
- Parity discipline: local builder reuses the worker's code unmodified — output provably identical.

## VERDICT

Not ready to call healthy: **B1 is an active week-long content outage** and B2 is a loaded data-loss gun. Both are fixable in under an hour once the owner picks the provider path (B1) and approves the self-heal gate deploy (B2). W1-W3 should land in the same pass so the unfrozen content actually reaches the site promptly and the poller can't wedge. Structure is sound — the bugs are at the seams (provider config, cache bridging, untested edges), not in the core model.

Recommended order: B1 provider fix + requeue → W1 bridge → B2 heal gate → W2/W3 poller hardening → W5 events logic → the rest.
